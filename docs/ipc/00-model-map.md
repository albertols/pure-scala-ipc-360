# 00 — Model map

Three-column map: IPC Powermart XML element/attribute → parser class that reads it
(`file:line`) → the recipe JSON key it ultimately produces. Element and attribute
spellings below are read directly from the corpus (see the provenance policy in
`README.md`) — for example `parser/src/main/resources/xmltobq/CDM/m_DM_INFOHUB_BIZLINK.xml:145-146`
(`<TRANSFORMATION NAME="SQ_ff_BIZLINK" ... TYPE="Source Qualifier">` containing
`<TRANSFORMFIELD DATATYPE="string" ... NAME="FCH_DATAENTRY" ... PORTTYPE="INPUT/OUTPUT" .../>`),
not transcribed from `powrmart.dtd`.

## IPC `Expression` transformations are not steps

`StepMode` (`StepMode.scala:5`) enumerates twelve values —
`SOURCE, UNION, FILTER, SOURCEQUALIFIER, JOINER, AGGREGATOR, TARGET, LOOKUP, ROUTER,
NORMALIZER, JAVA, STOREDPROCEDURE` — and has **no `EXPRESSION` value**.
`AbstractTarget` (`AbstractTarget.scala:6-89`) correspondingly has no expression
subclass. An IPC `<TRANSFORMATION TYPE="Expression">` is never itself a step target or
source; instead `RecipeGenerator.extractTransformationsFromInput` inlines it into the
enclosing field's transformation tree as an `EXP_*` call node
(`RecipeTransformationExpression { name, parameters? }`, `RecipeTransformation.scala:8`)
via the `(Expression, Output)` cases at `RecipeGenerator.scala:303-308`. So a chain of
Expression transformations between a source and a target does not add extra steps to
`Recipe.steps` — it only deepens the `transformation` tree on the one field that
ultimately reaches a real step target. This is why the corpus's per-kind step counts in
the design spec (§4) never include an `expression` entry alongside `table`,
`sourceQualifier`, `filter`, etc.
