# The IPC wiki

## What this is

This directory is ETL 360's own reference for the IPC (Informatica PowerCenter)
Powermart XML grammar and the platform-agnostic recipe (`_ETL_*.json`) model the
parser derives from it. It exists because Tab 2 (ETL Modifier) needs a
machine-checkable conformance ruleset — `backend/src/main/resources/ipc/ipc-rules.json`
plus the Java rule engine under `backend/src/main/java/io/pure360/etl360/service/ipc/`
— and that ruleset needs prose ground truth to cite instead of re-deriving it ad hoc
every time a rule is written or reviewed. See
`docs/superpowers/specs/2026-08-01-etl-modifier-redesign-design.md` §5 for the full
design; this wiki is that design's living reference material, not a duplicate of it.

Read this page first, then follow the index below into the construct you need.

## Provenance policy

`docs.informatica.com` returns **HTTP 403 to direct fetches** (verified 2026-08-01, on
both `designer-guide/mappings/validating-a-mapping.html` and its
`connection-validation` child page), while the same content is reachable through search
result summaries. Combined with the fact that `powrmart.dtd` and the PowerCenter guides
are Informatica's copyrighted material, this wiki follows three rules:

1. **Cite, don't vendor.** Every IPC-sourced rule carries an `ipcRef` URL. Short rule
   statements may be quoted with attribution; no page, guide or DTD is copied wholesale
   into this repo.
2. **Derive the element inventory from our own corpus.** The IPC XML element/attribute
   reference in this wiki (see `00-model-map.md`) is generated by reading the 81 corpus
   XMLs under `parser/src/main/resources/xmltobq`, not transcribed from the DTD. That
   also makes it more accurate for this tool specifically, which only ever sees exports
   of this one shape.
3. **The parser is the local authority.** Where IPC documentation and
   `parser/src/main/scala` disagree about what a construct means, this wiki records both
   readings, and the ruleset follows the parser — the ruleset's job is to keep recipes
   loadable by *this* pipeline, not to be a general PowerCenter conformance checker.

## The alias table

The committed corpus is anonymized sample data (`CLAUDE.md` corpus caveats: names like
MAPLEGROVE/CEDARFORGE are deliberate, not bugs). The anonymizer also touched four step
`type` values and one structural key, replacing the names
`parser/src/main/scala/io/pure360/ipc/model/recipe/` actually emits with unrelated
tokens. `IpcVocabulary`
(`backend/src/main/java/io/pure360/etl360/service/ipc/IpcVocabulary.java`) resolves
these tokens for validation and display only — **it never rewrites corpus bytes**.
Every mapping below is re-asserted against the real XML by
`backend/src/test/java/io/pure360/etl360/AliasWitnessContractTest.java`, so the table
can never silently drift from the data it claims to describe.

| Token | Kind | Canonical | Confirming witness |
|---|---|---|---|
| `BERYLFALLS` | step `type` | `sourceQualifier` | Step `SQ_ff_BIZLINK` of `CDM/m_DM_INFOHUB_BIZLINK.xml` is `<TRANSFORMATION NAME="SQ_ff_BIZLINK" TYPE="Source Qualifier">`. |
| `ASHPATH2` | step `type` | `joinerInput` | Step `JNR_Ashshore.DETAIL` of `DWH/m_DWH_MAPLEGROVE_ACT_CLIENTMGR_PROFILES.xml` is `<TRANSFORMATION NAME="JNR_Ashshore" TYPE="Joiner">`; the `.DETAIL` suffix comes from `AbstractTargetFactory.scala:88`, not the XML. |
| `CEDARWICK2` | step `type` | `storedProcedure` | Step `SWIFTVALE_BIRCHMILL_OAKFORD_P_MAIN` of `QDM/m_GENERATE_ERROR_BRISKGROVE.XML` is `<TRANSFORMATION NAME="SWIFTVALE_BIRCHMILL_OAKFORD_P_MAIN" TYPE="Stored Procedure">`. |
| `EARLYGLADE` | step `type` | `unionInput` | Step `LKP_CEDARMOOR_NETHUB_ELMYARD` of `CDM/m_DM_LKP_CONTACTREF_MEMBER_NETHUB_PAIR.xml` is **not** a `TRANSFORMATION` name — it is `<GROUP NAME="LKP_CEDARMOOR_NETHUB_ELMYARD" TYPE="INPUT">`, an input-group name. That is exactly what `createUnionTarget` (`AbstractTargetFactory.scala:51-55`) uses to name a `UnionInputTarget`, reading the `TRANSFORMFIELD@GROUP` attribute — a different evidence class from the other three tokens, which all name transformations directly. |
| `greencliff` (structural key) | `RouterTarget` key | `groups` | Step `RTR_CIPHERKEY_OFFERING` of `ETL/m_DWH_E_MAPLEGROVE_DEALFLOW_MIS_GCP1.xml` is `<TRANSFORMATION NAME="RTR_CIPHERKEY_OFFERING" TYPE="Router">`. Its `greencliff` value is a 14-entry array of `{name, filterCondition, default, fields}` objects — structurally identical to `RouterGroup` (`AbstractTarget.scala:47`) — so `greencliff` = `RouterTarget.groups` (`AbstractTarget.scala:44`), not `updateOverride` (that `Option` is `None` corpus-wide). |

One more key alias exists but has no XML witness to confirm, because it isn't an
anonymizer *substitution* — it is the pre-repair spelling of a real key: `weststone`
was `fields` before the 2026-07-31 key-rename repair (`CLAUDE.md` corpus caveats),
fixed in 64 recipes but still tolerated defensively by both the frontend recipe adapter
and `IpcVocabulary.canonicalKey`.

## Authority map

Different files are authoritative for different parts of the picture; when two sources
seem to disagree, this is the order to resolve it in:

| Question | Authoritative file |
|---|---|
| What shape does a step target/source kind have — which keys, which are optional? | `parser/src/main/scala/io/pure360/ipc/model/recipe/AbstractTarget.scala` (targets), `AbstractSource.scala` (sources) |
| What functions and operators can appear in an expression call tree? | `parser/src/main/scala/io/pure360/ipc/xmltojson/recipe/RecipeConstants.scala` (`PredefinedFunctions`, `ArithmeticOperators`, `ComparisonOperators`, `LogicalOperators`, `StringOperators`) |
| Is this rule an `error` or a `warning`, and why? | `backend/src/main/resources/ipc/ipc-rules.json` (severity is assigned by running the full catalogue over all 86 corpus recipes — zero violations ships `error`, any violation ships `warning`; see the design spec §5.4) |
| What does a construct mean in prose, with a citation? | This wiki (`docs/ipc/`) |

When IPC documentation and the parser disagree, the parser wins — this wiki records
both readings but the ruleset always follows `parser/src/main/scala`.

## Index

- **`00-model-map.md`** — the three-column map from IPC XML elements
  (`TRANSFORMATION@TYPE`, `TRANSFORMFIELD`, `TRANSFORMFIELD@GROUP`, `GROUP@TYPE`,
  `CONNECTOR`, `TABLEATTRIBUTE`, `INSTANCE`, `SOURCEFIELD`, `TARGETFIELD`) to the parser
  class that reads them and the recipe JSON key each one produces.
- **`rules.md`** — the full rule catalogue: id, statement, severity, `parserRef`,
  `ipcRef`, and for every `warning` the corpus evidence that forced the downgrade.
  Landed alongside `ipc-rules.json` and the rule engine (Part 1, later tasks of this
  plan).
- **`expressions.md`** — the `EXP_*` call-tree grammar, the `PredefinedFunctions` list,
  the four operator sets, and how `EXP_LOOKUP` differs from a plain call. Landed
  alongside the `IPC-EXP-*` rule family (Part 1, later tasks of this plan).
- **`transformations/<kind>.md`** — one page per step target/source kind (20 pages,
  `table` shared between target and source): what IPC says (cited), what the parser
  emits (`file:line`), the recipe JSON shape, required/optional keys, corpus occurrence
  count, a worked example from the corpus, and the rule ids that apply. Landed by Task 6
  of this plan.
